CHAPTER 01

Analytics 개요 & Reporting Logic (New)

Analytics for Group Reporting는 소거 전(Contribution) 또는 소거 후(Consolidated) 관점에서 데이터를 보여주는 분석 리포트 앱군입니다. 이 모든 앱의 밑바탕에는 하나의 공통된 Reporting Logic이 깔려 있습니다.

공통 전제조건

Analytics 앱을 실행하기 전에는 다음 Master Data·설정이 먼저 구성되어 있어야 합니다.

  • 조직 단위 Master Data(Consolidation Unit, Profit Center, Segment 등)
  • FS Item Hierarchy(예: 재무상태표·손익계산서 계층)
  • 필요 시 Reporting Rules 및 Reporting Item Hierarchy 설정

이 전제 위에서 필터를 적용해 재무상태표·손익계산서 등을 생성하고, 필요한 차원을 행/열로 자유롭게 추가하며, 최하위 노드(Leaf Node) 금액을 클릭해 전표 라인 항목까지 드릴스루할 수 있습니다.

💡 표준 지원 수준 · 커스텀 리포트

표준 화면 외에 직접 커스텀 리포트를 만들 수도 있습니다. Reporting Rules 없이 조회할 때는 CDS 뷰 C_CnsldtnGrpJrnlItemQ(쿼리 2CCSGRPJRNLITMQ)를, Reporting Rules를 적용해 조회할 때는 C_CnsldtnRuleBsdGrpJrnlItemQ(쿼리 2CCSRBGRPJRNLITMQ)를 사용합니다.

Reporting Logic은 SAP GR이 IFRS 판단을 대신 내려주는 추론 엔진이 아니라는 원칙을 그대로 반영합니다. 시스템은 Consolidation Group 정의, Hierarchy 정의라는 사전 구성된 Master Data 위에서 정해진 파생 규칙을 실행할 뿐이며, 어떤 관점(Group/Hierarchy/Combined)을 선택할지는 리포팅 목적에 따른 설계 결정입니다.

Case 1 — Hierarchical & Matrix Consolidation (ASPN 재구성)

ASPN Europe 리전 노드 아래 여러 유럽 법인이 편입되어 있다고 가정합니다. 원 Consolidation Unit 차원(Contribution View)으로 조회하면 ASPN Europe 리전의 매출 기여분이 그대로 나타나지만, Consolidation Unit Eliminated 차원으로 전환하면 ASPN Europe 노드 하위 법인들 사이의 내부거래만 소거되어 표시됩니다. 두 차원(CU / Profit Center)을 각각 행·열에 배치하면 리전 × 사업라인 매트릭스 리포트도 생성할 수 있습니다.

Case 3 — 복수 Consolidation Group에 동시 소속

ASPN Korea Manufacturing K200이 2025년 특정 시점부터 Top Group ASPN Holdings(그룹지분율 80%)와 서브그룹 ASPN Korea 지주(그룹지분율 75%)에 동시 편입되었다고 가정합니다. NCI(비지배지분)는 각 그룹별로 별도 계산되며, 델타 계산 없이 그룹마다 독립적으로 산출됩니다.

  • Top Group(ASPN Holdings) 관점 NCI = 로컬 순이익 × (1 − 80%)
  • 서브그룹(ASPN Korea 지주) 관점 NCI = 로컬 순이익 × (1 − 75%)
스탠딩 룰 · 데이터 범위 우선순위 — Consolidation Unit Hierarchy와 Consolidation Group을 함께 지정할 때는 두 데이터셋의 교집합이 존재해야 하며, 최종 데이터 범위는 항상 Consolidation Group 지정값이 우선합니다. 지정 그룹에 속한 CU가 지정 Hierarchy에 없는 경우, 해당 CU는 REST_H 노드 아래 별도 표시됩니다.
일반화 주의

이 세 케이스는 Reporting Logic이 어떻게 동작하는지 보여주는 예시일 뿐, "어떤 상황에서 어떤 필터 조합을 써야 한다"는 규칙을 시스템이 자동 판단해주지는 않습니다. Consolidation Method(구매법·지분법)와 그룹지분율은 여전히 Ownership Manager 구성과 프로젝트 설계에 따라 정해집니다.

CHAPTER 03

Reporting Items & Reporting Rules

현금흐름표, 자본변동표처럼 원 FS Item을 그대로 쓰기 어려운 리포트는, FS Item을 재가공하는 별도 계층 — Reporting Item — 을 통해 구현합니다.

개념 관계도

FS Item (Type=REPT)
Define FS Items 앱에서 생성
→
Reporting Item
Reporting Item Hierarchy에 편입
→
Reporting Rule
FS Item·CU·Doc Type 등 선택기준 할당
→
리포트
선택기준에 따른 집계값 표시

즉 Reporting Item은 그 자체로 하나의 통계적 FS Item이면서, 동시에 Reporting Rule에 정의된 선택 조건(예: FS Item 범위)에 해당하는 값들의 집계 결과를 대표합니다.

Define vs Manage Reporting Rules — 앱 선택 기준

구분Define Reporting RulesManage Reporting Rules
Master Data 해석 방식동적 해석(시간·버전 종속 속성 변화 반영)지정한 Selection Resolution Date 기준 고정 해석
사용 가능 차원Consolidation Unit, Subitem, FS Item, Document Type위 차원 + Profit Center, Segment 등 확장 차원(커스텀 필드 포함)
조건식단순 범위 선택 중심Greater Than / Not Equal / Like / Not Empty 등 복합 조건 가능

SAP 표준 Reporting Item Hierarchy (X1~X4)

  • X1 — Statement of Changes in Equity(자본변동표)
  • X2 — Statement of Cash Flow(현금흐름표)
  • X3 — Statement of Comprehensive Income(포괄손익계산서)
  • X4 — P&L by Function of Expense(기능별 손익계산서)

모든 규칙을 담은 표준 Reporting Rule Variant는 Y10입니다. Assign Reporting Rules to Versions 앱에서 이 Variant를 Report Rule Version에 매핑하고, 다시 Define Versions 구성에서 Consolidation Version과 연결하면 해당 버전에 규칙이 암묵적으로 적용됩니다.

주의 · Variant 불변성 — Report Rule Version에 한 번 할당된 Reporting Rule Variant는 이후 수정·추가가 불가능합니다. 의도치 않은 소급 변경으로부터 확정 리포트를 보호하기 위한 설계이며, 변경이 필요하면 기존 Variant를 복사해 새 Variant를 만들고 그 위에서 수정해야 합니다.
💡 "With Reporting Rules" 접미사

Group Data Analysis - With Reporting Rules처럼 앱 제목에 이 접미사가 붙으면 Reporting Item을 분석 차원으로 사용하며, Reporting Item Hierarchy와 Reporting Rule Variant 필터가 필수입니다. 접미사가 없는 앱은 Reporting Item·Hierarchy·Variant를 전혀 사용하지 않습니다.

Dynamic Mode — 시간종속적 조직 변경 반영

ASPN Tech가 연중 조직개편으로 리전 노드 3(ASPN 아시아)에서 노드 4(ASPN 글로벌 IT)로 소속이 변경되었다고 가정합니다. Dynamic Mode는 각 소속 구간(예: 노드 3 소속 1~3월, 노드 4 소속 4~12월)을 서로 겹치지 않는 고유한 유효기간(Validity)으로 관리하며, 입력한 Key Date에 해당하는 구간의 값만 표시합니다. 이를 통해 조직개편 전후 실적을 왜곡 없이 비교할 수 있습니다.

CHAPTER 06

Plan Consolidation & Restatement/Simulation

연결 결과를 계획(Plan)과 비교하거나, 이미 확정된 재무제표를 재작성(Restatement)·시뮬레이션해야 할 때 사용하는 두 기능입니다.

SAP Analytics Cloud(SAC) 연동 구조

Plan Consolidation은 SAC와의 통합을 전제로 합니다. SAP GR 공식 문서는 이를 Import Connection(Master/Transaction Data를 SAC로 추출해 계획 입력값으로 활용)과 Live Connection(데이터 물리적 복제 없이 실시간 조회)으로 구분하며, 다음 두 시나리오를 지원합니다.

  • 회계 레벨 계획 — S/4HANA Finance의 G/L계정·회사 Master Data 사용, Universal Journal(ACDOCA)에서 실적 추출 → SAC 계획 → Plan Data Line Items(ACDOCP)로 반영
  • 그룹 레벨 계획 — GR의 FS Item·Consolidation Unit Master Data 사용, Universal Consolidation Journal Entry(ACDOCU)에서 실적 추출
스탠딩 룰 · 최신 연동 방식 보완 — SAC의 S/4HANA Live Connection은 Datasphere 없이 SAP_COM_0065 통신 시나리오로 직접 OAuth 2.0 연결됩니다. 마찬가지로 ACDOCP Write-Back도 Datasphere 경유 없이 SAP_COM_0087 통신 시나리오로 직접 OData 연결됩니다. Datasphere는 비SAP 이기종 데이터 소스를 함께 결합해야 하는 경우에만 정당화되는 선택지입니다.

Restatement vs Simulation

Restatement는 회계기준·조직구조 변경 등으로 이미 공표된 재무제표를 다시 작성하는 것이고, Simulation은 "만약 ~라면"이라는 가상 시나리오의 결과를 확인하는 것입니다. 두 경우 모두 원본 버전을 그대로 보존한 채 Extension Version 위에서 처리합니다.

ASPN 예 — Version Stack 구성

ASPN Holdings가 표준 버전 Z10(EUR)을 사용 중, IFRS 18 도입과 경영조직 개편이라는 두 가지 재작성 사유가 동시에 발생한 경우를 가정합니다.

버전유형통화Reference Version
Z10Standard VersionEUR-
Z12Extension Version(IFRS 18 반영)EURZ10
Z13Extension Version(경영조직 개편 반영)EURZ12

Z13은 Z12 위에 쌓여 있으므로 Z12의 재작성 데이터에 접근할 수 있지만, 병렬로 생성된 다른 버전의 데이터에는 접근할 수 없습니다. 병렬 버전 간 데이터 이관이 필요하면 Copy Transaction Data 앱을 별도로 사용해야 합니다.

💡 Run Mode

Extension Version은 Manual Run(참조 버전과 별도 시점에 독립 실행) 또는 Automatic Run으로 설정합니다. Manual Run 버전에서는 ICMR Elimination 태스크와 Universal Journal Release 태스크가 지원되지 않으며, Task Group도 할당할 수 없습니다.

Balance Carryforward — Source/Destination 규칙

규칙내용
Source Version반드시 Extension Version이어야 함(Standard·Group Currency Extension 불가)
Destination VersionStandard·Extension·Group Currency Extension 모두 가능하나, Source와 동일한 Version Stack·그룹통화·회계연도 변형이어야 함
1:1 매핑동일 연도에 하나의 Destination에는 하나의 Source만 정의 가능
다단계 재작성Z12·Z13처럼 여러 Extension Version이 쌓인 경우, 최상위 버전(Z13)만 Source로 지정하면 그 아래 버전들의 데이터까지 함께 Destination(Z10)으로 이월됨
일반화 주의

Balance Carryforward를 정의된 연도 이외에 실행하면 이월 잔액은 일반 이월 Subitem에 기록되며, Deviating Carryforward Subitem은 적용되지 않습니다. 재작성 데이터의 출처를 재무제표에서 구분해서 보고 싶다면 Subitem Category 레벨에서 Deviating Carryforward Subitem을 사전에 활성화해야 합니다.
