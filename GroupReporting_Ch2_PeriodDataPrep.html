CHAPTER 01

결산 전 반드시 확인할 것: Period Preparation

데이터를 모으기 시작하기 전에, "잣대"와 "연결고리"가 먼저 맞아 있어야 합니다.

환율부터 맞추는 이유

여러 법인의 실적을 하나의 그룹통화로 합산하려면, 그 이전에 환율(Exchange Rate)이 준비되어 있어야 합니다. Group Reporting은 하나의 환율만 쓰지 않고, 용도별로 Exchange Rate Type을 구분해 관리합니다. 예를 들어 월평균환산에는 평균 환율(AVG), 월말 잔액환산에는 기말환율(CLO)을 쓰는 식입니다. 같은 통화쌍이라도 "언제, 어떤 목적으로" 쓰이는지에 따라 다른 값을 갖기 때문에, 이 구분을 섞으면 이후 통화환산 단계 전체가 틀어집니다.

Exchange Rate Type용도
AVG연결용 월평균환율
CLO연결용 기말환율
AVG1 / CLO1예산 연결용 평균/기말환율
AVG2 / CLO2연결 시뮬레이션용 평균/기말환율
INC2신규 편입 법인(Incoming Unit)용 환율

왜 "정합성 점검"이 준비 단계에 들어가는가

연결은 다른 회계 앱(예: 일반 회계, 자산 회계)에서 넘어온 데이터를 받아 처리합니다. 이때 송신 측과 수신 측의 설정이 어긋나 있으면 — 예를 들어 연결 계정과목(FS Item)이 총계정원장 계정과 매핑되지 않았거나, 수동으로 만든 Consolidation Unit이 실제 조직 단위와 연동되지 않았다면 — 데이터가 넘어와도 연결에 쓸 수 없습니다. Consistency Check of Accounting Integration은 이런 송수신 설정의 어긋남을 결산 전에 미리 찾아내는 역할을 합니다.

💡 실무 인사이트

환율 유지와 정합성 점검은 "매월 반복되는 단순 루틴"처럼 보이지만, 실제로는 이후 모든 태스크의 전제조건입니다. 환율이 비어 있거나 정합성 오류가 남아 있으면, Data Monitor의 통화환산· 검증 태스크가 실행 자체는 되어도 결과를 신뢰할 수 없는 상태가 됩니다. 그래서 이 두 가지는 "결산 체크리스트의 0번 항목"으로 다뤄야 합니다.

CHAPTER 02

데이터 준비의 관제탑: Data Monitor

모든 법인·모든 태스크의 상태를 하나의 화면에서 통제하는 구조입니다.

Data Monitor가 보여주는 것

Data Monitor는 법인(Consolidation Unit)별로 어떤 태스크가 어떤 상태인지를 표(조직 단위 × 태스크)로 보여줍니다. 태스크는 미리 정의되어 있고 순서가 있어, 앞 태스크가 끝나지 않으면 뒤 태스크로 넘어가도 의미 있는 결과가 나오지 않습니다.

표준화 완료 데이터 최종 검증 — Consolidation Monitor로 이관 전 마지막 관문

세 가지 실행 방식

  • Test Run — 상태·문서를 변경하지 않고 결과만 시뮬레이션
  • Update Run — 실제로 상태를 바꾸고 필요 시 문서를 생성
  • Test with Original List — 기간이 닫혀 있어도 상태·기간 체크 없이 실행 결과만 미리 확인

Block/Unblock — 진행 상태를 잠그는 장치

오류 없이 실행된 태스크는 Block 처리해 진행 상황을 고정할 수 있습니다. (Data Collection, Manual Posting은 실행 이력 없이도 Block 가능합니다.) 반대로 어떤 태스크를 Unblock하면, 그 뒤에 이어지는 모든 태스크가 자동으로 Unblock됩니다 — 예를 들어 Data Collection을 풀면 순이익 계산, 통화환산 등 하위 태스크가 전부 다시 열립니다. 이 연쇄 구조 때문에, 전체 상태가 초록불(Complete)이 되려면 관련 없는 태스크까지 포함해 전 태스크가 Block 상태여야 합니다.

일반화 주의 — Data Monitor는 법인(Consolidation Unit) 단위까지 태스크 실행이 가능하지만, Consolidation Monitor는 연결그룹(Consolidation Group) 레벨에서만 동작합니다. 두 모니터를 같은 개념으로 혼용하면 실무에서 "왜 이 앱에서는 법인별로 안 보이지"라는 혼란이 생깁니다.

CHAPTER 03

결산의 출발점: 이월과 저널 반영

전기 잔액을 넘겨받고, Universal Journal을 연결 관점으로 끌어오는 첫 두 태스크입니다.

Balance Carryforward — 왜 항상 첫 번째 태스크인가

Balance Carryforward는 전기(prior year) FS Item 잔액을 당기 기초로 이월하는 태스크입니다. 이 값이 틀리면 이후 모든 태스크가 잘못된 기초 위에서 계산되기 때문에, Data Monitor 태스크 순서에서 항상 가장 앞에 위치합니다.

Release Universal Journal — 4가지 모드가 존재하는 이유

Release Universal Journal은 Universal Journal에 기록된 회계 데이터를 Group Reporting이 연결 관점에서 조회·반영할 수 있도록 끌어오는 태스크입니다. 이때 "이번 기간 것만 볼지, 과거 기간도 다시 볼지"와 "전체를 다시 반영할지, 변화분만 반영할지"라는 두 축이 조합되어 4가지 모드가 존재합니다.

Current Period

  • Complete Data — 이번 기간 전체 데이터를 다시 반영
  • Delta — 이번 기간 중 변경분만 반영

Prior Periods

  • Complete Data — 과거 기간 전체를 다시 반영(뒤늦게 들어온 전기 항목 등)
  • Delta — 과거 기간 중 변경분만 반영

Extension Version과 다중 그룹통화 반영

Standard Version에 참조를 걸고 있는 Extension Version이 있는 경우, Release Universal Journal은 두 버전을 하나의 묶음(Bundle)으로 함께 실행합니다. 다만 로그는 Standard Version 기준으로만 표시되며, Extension Version의 로그는 Task Log 앱에서 별도로 조회해야 합니다. 법인의 현지통화가 Standard Version 그룹통화와는 같지만 Extension Version 그룹통화와는 다른 경우, 통화환산 태스크는 "해당 없음(Irrelevant)"으로 처리되지 않고 실제로 실행됩니다 — 즉 버전마다 그룹통화가 다르면 같은 법인이라도 태스크 관련성이 달라질 수 있습니다.

일반화 주의 — Universal Journal의 데이터가 ACDOCA에 직접 반영된다는 식으로 단순화할 수 없습니다. Group Reporting은 Release Universal Journal이라는 표준 태스크를 통해 데이터를 읽어와 그룹 저널에 반영하는 구조이며, 이 과정에서 표준화·환산 등 여러 단계를 거칩니다.
💡 실무 인사이트

Standard Version과 Extension Version(Manual Run Mode)이 함께 존재할 때는 기간 개폐 순서도 엮여 있습니다. Standard Version에서 기간을 열면 참조 중인 Extension Version도 자동으로 열리지만, 반대로 Extension Version은 참조 대상인 Standard Version의 기간이 먼저 닫히기 전까지는 닫히지 않습니다. 재작성(Restatement)·시뮬레이션 작업을 하는 담당자라면 이 순서를 모르고 "왜 기간이 안 닫히지"라는 혼란을 겪기 쉽습니다.

CHAPTER 04

데이터가 들어오는 경로들: Data Collection

모든 법인이 같은 방식으로 데이터를 넣는 것은 아닙니다.

하나의 태스크, 여러 개로 쪼갤 수 있는 이유

Data Collection은 기본적으로 하나의 태스크(1020)이지만, Data Monitor 설정을 통해 문서 유형(Document Type)별로 여러 개의 수집 태스크로 나눌 수 있습니다. 예를 들어 "문서유형 1은 A팀이, 문서유형 2·3은 B팀이, 문서유형 4는 C팀이 담당"하는 식으로 나누면, 담당자별 책임 구분과 상태 추적이 명확해집니다. 이는 단순 편의 기능이 아니라 업무 분장(Segregation of Duties)을 시스템 구조로 반영하는 방법입니다.

세 가지 대표 입력 경로

  • 수동 입력(Manual) — Data Monitor 화면에서 직접 값을 입력하거나 조정
  • Flexible Upload — 정해진 템플릿 파일로 대량의 보고 데이터·그룹 저널 전표를 일괄 업로드
  • SAP Analytics Cloud 연동 — SAC에서 수립한 계획(Plan) 데이터를 Export Configuration을 통해 내보내고, Group Reporting에서 이를 가져와(Import) 계획 버전 데이터로 반영

CHAPTER 05

표준화 엔진: 순이익 계산과 통화환산

서로 다른 법인의 데이터를 "같은 잣대"로 만드는 두 개의 핵심 태스크입니다.

Calculate Net Income — 왜 필요한가

법인이 보고하는 데이터는 보통 시산표(Trial Balance) 형태로, 재무상태표와 손익계산서를 합치면 균형이 맞지만 각각 따로 보면 균형이 맞지 않는 상태입니다. Calculate Net Income 태스크는 손익 항목을 합산해 당기순이익을 계산하고, 이를 재무상태표와 손익계산서 양쪽에 반영해 두 보고서가 개별적으로도 균형을 이루도록 만듭니다.

Currency Translation — 하나의 방법이 아니라 "여러 방법 중 선택"

통화환산은 로컬통화 잔액을 그룹통화로 바꾸는 태스크이지만, 상황에 따라 적용해야 할 논리가 다릅니다. 신규로 편입된 법인은 편입 시점 환율을 기준으로 환산해야 하고, 일반 법인은 표준 기간별(Periodic) 환산을 쓰며, 지분법·연결조정 관련 항목은 활동기준(Activity-Based) 환산이 필요할 수 있습니다. 이런 차이를 반영하기 위해 Group Reporting은 여러 개의 사전 정의된 Translation Method를 제공하고, 법인·시나리오별로 어떤 방법을 적용할지 매핑합니다.

대표 시나리오 A

  • 신규 편입 법인 — 편입 시점 환율 기준 환산
  • 연도 누계(YTD) 기준 환산이 필요한 법인

대표 시나리오 B

  • 일반 법인 — 표준 기간별(Periodic) 환산
  • 투자 관련 활동(COI) — 활동기준 환산
일반화 주의 — 어떤 Translation Method를 어떤 법인·FS Item에 적용할지는 시스템이 자동으로 판단해주지 않습니다. 그룹의 회계정책과 연결 시나리오(신규 편입, 처분, 지분법 전환 등)에 따라 프로젝트에서 명시적으로 설계·매핑해야 하는 영역입니다.
💡 실무 인사이트

통화환산 결과에 차이(Difference)가 남는 것은 오류가 아니라 환산 방식 자체의 특성입니다. 예를 들어 누계값 환산과 기간값 환산은 같은 원本 데이터에서도 다른 차이금액을 만들어냅니다. 이 차이가 어디서 발생했는지 설명하지 못하면, 감사 대응 시 "왜 이 금액이 나왔는지 모른다"는 가장 곤란한 상황을 맞게 됩니다.

CHAPTER 06

검증은 한 지점이 아니다: Data Validation 체계

데이터가 나쁜 상태로 다음 단계에 넘어가지 않도록, 서로 다른 시점에 서로 다른 것을 검증합니다.

왜 검증 태스크가 하나가 아니라 세 개인가

Data Monitor에는 성격이 다른 세 번의 검증이 순차적으로 배치되어 있습니다. 각 검증은 "그 시점까지 처리된 데이터"만을 대상으로 하기 때문에, 하나로 합칠 수 없습니다.

일반화 주의 — 신규 Group Reporting 로직이 활성화된 환경에서는 S0080(Accounting Data Validation), S1080/S1180 같은 별도 검증 태스크 체계가 쓰이기도 합니다. 어떤 체계가 적용되는지는 시스템 설정에 따라 다르므로, 태스크 ID를 프로젝트마다 동일하다고 단정할 수 없습니다.

CHAPTER 07

수작업이 필요한 순간: Manual Posting & Group Journal Entries

자동 태스크가 처리하지 못하는 예외는, 통제된 방식의 수작업으로 흡수합니다.

Posting Level로 구분되는 수작업의 성격

Data Monitor 안의 수작업은 성격에 따라 Posting Level로 구분됩니다. 예를 들어 Posting Level 01은 "보고 데이터 자체를 수동으로 고치는 것", Posting Level 10은 "표준화 단계에서 수동으로 재분류하는 것"입니다. 소거·연결조정처럼 더 상위 단계의 수작업 (Posting Level 20, 30)은 Data Monitor가 아니라 Consolidation Monitor에서 이뤄집니다.

Group Journal Entries — 직접 입력 vs 일괄 업로드

그룹 저널 전표는 화면에서 직접 입력할 수도 있고, 정해진 템플릿 파일로 일괄 업로드할 수도 있습니다(헤더 데이터 → 라인아이템 입력 → 검증 → Post 순서). 이연법인세 반영, 특정 FS Item 대상 전기처럼 반복 패턴이 있는 작업은 업로드 경로가 효율적이고, 예외적·개별 건은 직접 입력이 더 적합합니다.

다중 그룹통화·다중 연결그룹 환경에서의 수작업

하나의 Standard Version에 여러 그룹통화 버전(예: EUR 기준 Standard, USD Extension)이 연결되어 있다면, 수동으로 입력한 그룹 저널 전표도 관련된 모든 그룹통화 버전에 반영되어야 합니다. 마찬가지로 하나의 법인이 여러 연결그룹에 동시에 속해 있다면, 그룹 저널 전표를 어느 연결그룹에 반영할지도 함께 지정해야 합니다.

재작성(Restatement)·시뮬레이션에서의 수동 전기

재작성이나 시뮬레이션 작업은 Manual Run Mode의 Extension Version을 열어 진행합니다. 이 경우 Standard Version의 전표 문서와 Extension Version의 전표 문서는 별도로 관리되며, 어떤 버전을 대상으로 전기했는지 항상 명확히 구분해야 합니다.

일반화 주의 — 수동 전기가 많다고 해서 그 자체가 "설계가 잘못됐다"는 신호는 아닙니다. 다만 반복적으로 같은 유형의 수동 조정이 발생한다면, 이는 Posting Rule(자동 전기 규칙)로 흡수할 수 있는지 검토해야 할 신호로 봐야 합니다.

CHAPTER 08

신뢰의 기반: Balance Validation과 거버넌스

시스템 표준 검증만으로 잡히지 않는 "우리 그룹만의 규칙"을 확인하는 별도 체계입니다.

Data Monitor 검증과 무엇이 다른가

Ch.6에서 다룬 세 가지 검증(Line Item / Reported / Standardized)이 시스템 표준 로직에 가깝다면, Balance Validation은 그룹이 직접 정의한 Rule과 이를 묶은 Rule Group으로 동작하는 커스텀 검증입니다. 예를 들어 "A FS Item과 B FS Item의 차이가 특정 범위를 넘지 않아야 한다"처럼, 그룹 고유의 재무 로직을 규칙으로 등록해 법인 단위 또는 연결그룹 단위로 실행합니다.

Rule Group 구조

Rule Group 안에는 여러 개의 Rule이 있고, Rule은 다시 단순 비교식인 Basic Rule과 여러 Basic Rule을 조합한 Compound Rule로 나뉩니다. 검증 결과는 법인·연결그룹 별로 집계되어, 어느 조합에서 규칙 위반(경고/오류)이 발생했는지 드릴다운으로 원천 데이터까지 추적할 수 있습니다.

권한 설계 — 아무나 규칙을 바꿀 수 없어야 하는 이유

Balance Validation은 Consolidation Unit, Consolidation Group, Consolidation Version, Task Category(법인 단위/그룹 단위 검증 구분) 같은 필드를 기준으로 권한을 제한할 수 있습니다. 이를 통해 "누가 규칙을 설계할 수 있는지"와 "누가 결과만 조회할 수 있는지"를 분리해서 운영할 수 있습니다.

💡 실무 인사이트

Balance Validation 결과는 재검증(Revalidate)해도 이전 결과에 남긴 코멘트가 유지됩니다. 이 특성 덕분에 "언제, 누가, 왜 이 오류를 예외 처리했는지"에 대한 이력을 남길 수 있어, 외부 감사 대응 시 근거 자료로 활용할 수 있습니다. 규칙을 설계할 때부터 "이 결과를 나중에 누구에게 설명해야 하는가"를 염두에 두는 것이 좋습니다.

일반화 주의 — Balance Validation의 커스텀 필드 확장은 법인 단위·그룹 단위 검증 Task Category에 한해 가능하며, 모든 검증 시나리오에 무제한으로 적용되는 기능은 아닙니다.
